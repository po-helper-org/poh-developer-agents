# Обвязка целевого репозитория

Что положить в репозиторий, который берётся под контур производства. Файлы
здесь — образец, снятый с `poh-demo-checkout`; копируются по тем же путям.

```
target-repo/
├── AGENTS.md                              → <repo>/AGENTS.md
├── CLAUDE.md                              → <repo>/CLAUDE.md
├── .openhands/task-rules.md               → <repo>/.openhands/task-rules.md
├── .delivery/checks.json                  → <repo>/.delivery/checks.json
└── .github/workflows/
    ├── ci.yml                             → <repo>/.github/workflows/ci.yml
    ├── openhands-resolver.yml             → только для режима `dispatch`
    └── pr-review.yml                      → только для режима `dispatch`
```

## Что обязательно, а что нет

| Файл | Режим `local` | Режим `dispatch` | Если нет |
|---|---|---|---|
| `.openhands/task-rules.md` | **обязателен** | **обязателен** | постановка уедет агенту без правил проекта |
| `AGENTS.md` | желателен | желателен | агент не знает структуру и конвенции |
| `CLAUDE.md` | желателен | желателен | нет полного свода правил, на который ссылается `AGENTS.md` |
| `ci.yml` | желателен | **обязателен** | нечем проверить PR от человека |
| `openhands-resolver.yml` | не нужен | **обязателен** | диспатчить нечего |
| `pr-review.yml` | не нужен¹ | **обязателен** | ревью не запустится |
| `.delivery/checks.json` | желателен | желателен | релиз пойдёт, но подтверждать поведение будет нечем, кроме факта запуска сервиса |

¹ В режиме `local` ревью делает self-hosted PR-Agent по вебхуку GitHub App.
Вход `pull_request` в `pr-review.yml` оставлен именно для этого случая как
дублёр: PR открывает агент разработки, живущий не в Actions, и его токен —
не `GITHUB_TOKEN`, поэтому правило GitHub против рекурсии не действует и
событие приходит.

## Секреты и переменные репозитория

Нужны только в режиме `dispatch` — их читает прогон в Actions, единственная
часть контура, которая живёт не на стенде.

| Секрет | Значение |
|---|---|
| `LLM_API_KEY` | ключ модели (тот же, что `ZAI_API_KEY` харнесса) |
| `ISSUE_AGENT_URL` | `<PUBLIC_URL>/issue` |
| `AGENT_EVENT_SECRET` | **та же строка**, что в `.env` харнесса |
| `PAT_TOKEN` | опционально; нужен, только если ревью переведут на Actions по событию `pull_request` |

Переменные (`vars`): `LLM_MODEL`, `LLM_BASE_URL`, `PR_AGENT_MODEL` — у всех
есть умолчания в workflow.

> **`503` на `/issue/agent-event` — самая дорогая из возможных ошибок
> конфигурации.** Всё остальное работает, задачи доходят до разработки, PR
> открываются — и ни одна задача не закрывается, потому что доклад о PR
> отвергается на входе. Симптом неотличим от «агент разработки завис».

## Что должно быть в самом репозитории, а не в файлах обвязки

- **Команда проверок**, одна и та же для CI, для агента и для гейта стадии
  (`DEVELOP_TEST_COMMAND`). Разъезд этих трёх — красный шаг разработки на
  зелёном коде.
- **Раздел HowToDemo** в теле каждой задачи — граница MVP. Без него у стадии нет
  критерия остановки.
- **`.harness/`** — контекст задачи в файлах. Коммитится вместе с кодом
  намеренно: это задача, а не отчёт о прогоне.

## Известное расхождение

`AGENTS.md` и `.openhands/task-rules.md` описывают механику находок через
**SubIssue**. Контур так больше не делает: находки дописываются строками в
секцию **GROW** тела родительского Issue, и Issue по ним заводит человек после
гейта приёмки. Правила — это постановка, уезжающая агенту дословно, поэтому
расхождение подлежит правке; см. [`../docs/gaps.md`](../docs/gaps.md), **G5**.
