# AGENTS.md

Постоянный контекст для агентов, работающих в этом репозитории. Полный свод
правил — [`CLAUDE.md`](CLAUDE.md); здесь то, что обязано быть в голове ДО первой
правки.

## Назначение репозитория

`poh-demo-checkout` — маленький сервис расчёта стоимости заказа. Он существует
не ради себя: на нём гоняется полный цикл контура производства — Issue →
аналитика → разработка → PR → ревью. Код намеренно простой, чтобы предметом
разбора был контур, а не предметная область.

## Структура

- `src/pricing.mjs` — вся арифметика. Чистые функции без ввода-вывода
- `src/server.mjs` — тонкая HTTP-обёртка: разбор запроса и коды ответов
- `tests/pricing.test.mjs` — тесты расчёта (`node:test`)

Зависимостей нет — это свойство сервиса, а не упущение. Новая зависимость
заводится, только если задачу нечем закрыть из стандартной библиотеки, и причина
записывается рядом с кодом.

## Проверки

Та же команда, что гоняет CI (`.github/workflows/ci.yml`):

```bash
node --test "tests/*.test.mjs"
```

Новая логика — новый тест. Правка расчёта без теста на неё считается
незавершённой: расчёт здесь единственное, что вообще может сломаться молча.

## Как агент ведёт работу

**MVP первым, edge-кейсы — в SubIssue.** Граница MVP — раздел **HowToDemo** в
Issue. Пока HowToDemo не проходит, делается только то, что к нему ведёт.

Найденный по дороге edge-кейс, риск или «надо бы потом учесть» **не чинится в
текущей ветке** — он записывается в `.followups.md` в корне рабочего каталога,
по одному разделу на находку:

```markdown
## Отрицательная цена позиции проходит в расчёт

`subtotal` проверяет `price < 0` уже после умножения на `qty`
(src/pricing.mjs:26). Всплывёт на импорте прайса из внешней системы.
```

SubIssue по находкам заводит контур: своим токеном, с меткой `origin:agent` и
ключом цепочки `root-issue: #N` в теле, и сам оставляет ссылки комментарием в
родителе. По этим двум признакам контур отличает свой выход от входа: Issue с
`origin:agent` проходит сокращённый триаж, а follow-up, порождённый
follow-up-ом, уходит человеку вместо второго круга. Без них каждый PR начинал бы
рождать Issue, а каждый Issue — PR.

Заводить их самому нечем и не нужно: `gh` и GITHUB_TOKEN агенту разработки не
дают намеренно — он исполняет код репозитория, и токен рядом с этим кодом лишний.

**Ветка и PR несут номер Issue.** Ветка — `feature/<N>-<slug>`, PR — `Closes #N`
в теле. Это сквозной ключ: по нему Issue-Agent и PR-Agent собирают один таймлайн
из двух сервисов.

**Хронология непрерывна.** Значимый шаг — комментарий в Issue, а не только в
логе прогона: следующий агент восстанавливает контекст чтением одного Issue.

## Чего не делать

- Чинить edge-кейс «раз уж он рядом» и расширять scope ветки находками, не
  блокирующими HowToDemo.
- Заводить зависимость ради того, что закрывается стандартной библиотекой.
- Переписывать `src/server.mjs` арифметикой: расчёт живёт в `pricing.mjs` и
  проверяется без сети. Логика в обёртке — логика, которую тест не увидит.
