# Замечания человека в ревью доходят до контура

Дата: 2026-09-03
Состояние: замысел к валидации

## Откуда задача

`po-helper-org/poh-demo-checkout#172`, 3 сентября.

- 04:40 и 04:50 контур дважды прогнал круг правок по автоматическому ревью и
  заключил: «агент не нашёл в ревью того, что требует изменений в коде. **PR
  готов к слиянию** и ждёт решения разработчика».
- 05:32 человек оставил формальное ревью GitHub со статусом
  `CHANGES_REQUESTED` и двумя замечаниями, одно из которых — регрессия,
  введённая самим PR: `Allow: GET` перестал быть правдой, когда HEAD стал
  разрешённым методом.
- Реакции не было и быть не могло. Замечание пришлось закрывать руками.

## Что именно сломано

**Не чтение, а побудка.** `github_client.review_text` (`worker/github_client.py:892`)
уже ходит в `/pulls/{n}/reviews` и берёт тело ревью вместе с состоянием, а
также построчные замечания из `/pulls/{n}/comments`. Если бы круг правок
запустился, замечание человека до агента дошло бы.

Не запускается он потому, что **событий ревью контур не получает**:

- вебхук репозитория подписан на `issues, issue_comment, label, pull_request,
  sub_issues` — `pull_request_review` в списке нет;
- обработчика `pull_request_review` в `webhook/main.py` нет тоже.

Ревью PR-Agent доходит только потому, что тот дополнительно пишет **обычным
комментарием** и докладывает через `/agent-event`. То есть путь работает по
совпадению формы, а не потому, что ревью обрабатывается как ревью.

**Второе, независимое:** `pr_closing.settled_comment` объявляет «PR готов к
слиянию», не спрашивая GitHub, готов ли он. При `CHANGES_REQUESTED` слияние
заблокировано, и утверждение ложно.

## Что решаем

1. Формальное ревью человека будит круг правок так же, как доклад PR-Agent.
2. Контур не называет готовым к слиянию PR, слияние которого заблокировано.

## Требования

### Побудка

**R1.** Вебхук принимает событие `pull_request_review` и доводит его до
`IssueLifecycle` тем же путём, каким туда попадает доклад PR-Agent, — как
переход в фазу `pr-review`.

Отдельной ветки решения для человеческого ревью не заводим: круг правок уже
умеет читать замечания любого происхождения, и вторая ветка означала бы два
пути к одному действию и два места для расхождения.

**R2.** Событие `pull_request_review_comment` (построчное замечание без
формального ревью) будит круг так же. `review_text` построчные замечания уже
читает, и оставить их без побудки значило бы починить половину.

**R3.** Будят состояния `changes_requested` и `commented`. Состояния
`approved` и `dismissed` не будят: править по одобрению нечего, а снятое
ревью — не замечание.

**R4.** Ревью, оставленное **ботом**, по этому пути не будит ничего. PR-Agent
докладывает через `/agent-event`, и вторая побудка от него дала бы два круга
на один доклад.

**R5.** Побудка проходит тот же allowlist автора, что и прочие дорогие
триггеры (`may_trigger`, `AGENT_TRIGGER_ALLOWLIST`). Круг правок стоит прогона
агента, и запускать его по ревью произвольного участника нельзя.

**R6.** Событие без связанного Issue (PR не заводился контуром) роняется в
аудит, как это уже делают прочие необработанные события, а не поднимает
воркфлоу.

### Готовность к слиянию

**R7.** «PR готов к слиянию» говорится только тогда, когда GitHub его слить
даёт. Состояние ревью читается фактом, а не выводится из того, что агент не
нашёл предмета для правок.

**R8.** При `CHANGES_REQUESTED` итог круга правок называет вещи своими
именами: замечания остаются неснятыми, решение за человеком. Метка очереди к
людям ставится, как и при исчерпании кругов.

**R9.** Проверка состояния ревью **не имеет права ронять** итог круга: не
удалось спросить GitHub — говорим прежним текстом, но без утверждения про
готовность.

### Подписка

**R10.** Подписку вебхука на новые события нужно проставить в двух местах:
хук репозитория и настройки GitHub App. Это ручная эксплуатационная операция,
и она **не** делается кодом этой работы — но без неё код не сработает, и это
записано в README рядом с описанием пути.

**R11.** Отсутствие подписки не выглядит как исправная работа: если контур
получает `pull_request` по репозиторию, но никогда `pull_request_review`,
понять это по логам нельзя. Явной проверки не заводим — она стоила бы дороже
пользы, — но README называет симптом: замечания человека молча ни к чему не
приводят.

## Пограничные случаи

| Случай | Поведение |
|---|---|
| Человек оставил `CHANGES_REQUESTED` | Круг правок запускается (R1, R3) |
| Человек оставил `COMMENTED` с замечаниями | То же (R3) |
| Человек одобрил PR | Ничего не запускается (R3) |
| Ревью оставил бот | Ничего: доклад придёт через `/agent-event` (R4) |
| Построчное замечание без ревью | Круг правок запускается (R2) |
| Автор ревью не в allowlist | Не запускается, отказ пишется в лог (R5) |
| PR не связан с Issue контура | Событие уходит в аудит (R6) |
| Агент не нашёл предмета, но стоит `CHANGES_REQUESTED` | «Готов к слиянию» НЕ говорится (R7, R8) |
| GitHub не ответил на запрос состояния | Итог публикуется без утверждения о готовности (R9) |
| Подписки на событие нет | Ничего не происходит; симптом описан в README (R10, R11) |

## Чем проверяется

- Событие `pull_request_review` со статусом `changes_requested` от человека
  доводит задачу до круга правок.
- То же для `pull_request_review_comment`.
- `approved` и ревью бота не запускают ничего.
- Автор вне allowlist не запускает ничего.
- Событие без связанного Issue уходит в аудит и не роняет вебхук.
- Итог круга при `CHANGES_REQUESTED` не обещает готовности и ставит метку
  очереди к людям.
- Отказ запроса состояния ревью не роняет публикацию итога.
- Гвард реплея зелёный; правки решений под маркерами.

## Вне границ

- **Автоматическое снятие `CHANGES_REQUESTED`** после правок. Снять своё
  ревью может только его автор, и делать это за него контур не должен.
- **Ответ на замечание репликой в тред.** Круг правок правит код и пишет
  разбор итогом; спор в тредах — отдельная работа.
- **Событие `pull_request_review` для GitLab.** У GitLab своя модель ревью;
  адаптация — часть работ по GitLab (#141, #275, #276).
- **Проставление подписки кодом.** Эксплуатационная операция (R10).
