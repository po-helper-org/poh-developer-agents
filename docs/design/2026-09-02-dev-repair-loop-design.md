# Разработка чинит свою поломку

Дата: 2026-09-02
Состояние: замысел согласован, к реализации

## Откуда задача

Два живых прогона разработки подряд, 2 сентября 2026, оба на
`po-helper-org/poh-demo-checkout`:

- `#166` — агент отработал тринадцать минут, `dev_tests` упал, работа исчезла;
- `#167` — то же самое, но работа спаслась черновиком (PR #295, смержено).

Оба прогона кончились человеком, и **ни в одном из них агент ничего не
ломал**. `main` демо-репозитория красный с 1 сентября: промокод `SUMMER20`
имеет `activeUntil: '2026-09-01'` (`src/pricing.mjs:23`), `validatePromoCode`
отсекает его по текущей дате (`:82`).

CI репозитория гоняет тесты на каждый коммит в `main` — но последний прогон
там был **28 августа, зелёный**. Тест покраснел сам, по календарю, без единого
коммита. Прогона не было, и никто не узнал.

**CI не ловит бомбы с часовым механизмом.** Просроченный промокод, истёкший
сертификат в фикстуре, зависимость, сменившая поведение, — любой репозиторий
может оказаться красным без чьего-либо ведома.

Но красный `main` — только повод. Настоящая задача крупнее: прогон разработки
заканчивается человеком **независимо от того, годный код написал агент или
нет**. `_dev_tests` (`worker/activities.py:3252`) бросает `RuntimeError` на
любом ненулевом коде возврата, и на этом всё.

## Что решаем

Прогон разработки доводит работу до конца сам:

1. отличает свою поломку от чужой и от мигающего теста;
2. **чинит свою** — одним повторным заходом агента;
3. человека зовёт только тогда, когда починить не вышло.

Различение своего и чужого — не самоцель, а вход для починки: чинить, не
отличив, значит посылать агента править чужой код.

## Как выглядит

`#167` при работающем механизме:

- агент правит `src/server.mjs`, `dev_tests` даёт три падения;
- прогон снимает базовую линию — те же три теста красные и без агента;
- разница пуста, **своих поломок нет** → обычный PR, в теле строка про три
  чужих падения;
- человек не зовётся вовсе.

Если бы агент сломал четвёртый тест: этот тест перепроверяется на мигание,
подтверждается, агент идёт **на второй заход** с текстом только про своё
падение. Починил — обычный PR. Не починил — отказ, черновик, человек.

## Порядок шагов

Ключевое решение: **всё дополнительное платится только на красном прогоне.**
Зелёный прогон не стоит ни одной лишней секунды.

```
dev_prepare → dev_run_agent → dev_followups → dev_tests
                                                 │
                            зелено ──────────────┴──→ dev_publish (как сегодня)
                                                 │
                            красно ──→ базовая линия (чистое дерево)
                                       повторный прогон (дерево агента)
                                       свои = (после₁ ∩ после₂) − до
                                                 │
                            своих нет ───────────┴──→ dev_publish + оговорка
                                                 │
                            свои есть ──→ повторный заход агента
                                          dev_tests снова
                                                 │
                            починил ─────────────┴──→ dev_publish
                            не починил ──────────────→ отказ + черновик
```

## Требования

### Различение своего и чужого

**B1.** Базовая линия снимается **только когда итоговый прогон красный**.
Зелёный прогон в ней не нуждается: своих поломок в нём нет по определению.

**B2.** Базовая линия гоняется на **отдельном чистом рабочем дереве** от
базового коммита (`git worktree add`), а не прятанием правок агента
(`git stash`).

Прятать нельзя категорически: сорванный `stash pop` уничтожает работу агента —
ровно то, что контур только что научился спасать черновиком (PR #295). Механизм
проверки не имеет права уничтожать то, что проверяет.

**B3.** Свои поломки = **устойчиво** упавшие после правки минус упавшие до неё.

**B4.** Имена упавших тестов читаются из отчёта **JUnit XML**, а не из текста
вывода: `<testcase>` с вложенным `<failure>` или `<error>`, имя собирается из
`classname` и `name` — одного `name` мало, одинаковые имена в разных наборах
обычны.

Разбор stdout привязал бы механизм к знакомым раннерам. JUnit XML пишут Maven и
Gradle сами без флагов, pytest по `--junit-xml`, `node --test` по
`--test-reporter=junit` (проверено фактом 2026-09-02), PHPUnit по `--log-junit`.

**Оговорка о сегодняшней пользе:** репозитории организации — Python и Node, то
есть ровно те два раннера, чей текстовый вывод пришлось бы разбирать иначе.
Прямо сейчас XML не расширяет охват, он снимает будущую правку под каждый новый
стек. Выбран ради этого, а не ради мнимой немедленной общности.

**B5.** Отчёт ищется по путям из `DEVELOP_TEST_REPORT` (несколько через
запятую). Умолчание покрывает `**/junit*.xml`, `target/surefire-reports/*.xml`,
`build/test-results/**/*.xml`.

### Мигающие тесты

**B6.** Падение, отсутствующее в базовой линии, **перепроверяется повторным
прогоном набора** на дереве агента. Своим считается только то, что упало **оба
раза**.

Мигающий тест падает в итоговом прогоне и не падает в базовом — и без этой
проверки вменяется агенту. Это то же неверное вменение, ради устранения
которого пишется вся работа, только с другой стороны.

**B7.** Перепрогоняется **весь набор**, а не отдельные подозрительные тесты.
Выбор отдельных тестов требует синтаксиса конкретного раннера — той самой
привязки, от которой уходит B4.

**B8.** После повторного захода агента проверка на мигание **не повторяется**:
подозрительные тесты уже подтверждены дважды, а новые падения появились после
правки, которую агент только что делал.

### Круг правок

**B9.** Свои поломки есть — агент идёт на **повторный заход** в том же рабочем
дереве, со своей правкой на месте. Начинать с чистого дерева нельзя: это не
починка, а второй прогон задачи с нуля.

**B10.** Заход **один**. Не починил со второй попытки — отказ и человек.

Второй заход удваивает худший случай прогона (агент идёт до 45 минут). Число заходов — настройка `DEVELOP_REPAIR_ROUNDS` с умолчанием 1, а не
константа: поднять его можно, когда
появится статистика, сколько починок удаётся.

**B11.** На повторный заход агент получает: **только свои** падения, их вывод
из отчёта и указание, что чужие падения трогать не нужно.

Чужие падения в текст не идут ни в каком виде. Агент, увидевший четыре
поломки вместо одной, пойдёт чинить чужой код — и это худший исход, чем отказ:
правка чужого приедет в PR под видом решения задачи.

**B12.** Повторный заход — **отдельная активность**, а не флаг у
`dev_run_agent`: свой шаг в истории Temporal, свой таймаут, видимый факт
«контур пробовал починить».

**B13.** После починки свои поломки считаются против **той же** базовой линии.
Заново её не снимают: базовый коммит не менялся, а лишний прогон набора стоит
времени.

**B14.** Своих поломок нет после починки — прогон **удался**, PR обычный.

### Осторожность там, где не знаем

**B15.** Исход **не разобран** — отчёта нет, он битый, тестов в нём ноль —
контур ведёт себя **как сегодня**: ненулевой код возврата считается отказом,
починка не запускается.

Это касается любого конца: неразобранная база означает, что послабления и
починки не будет, даже если после агента отчёт прочитался.

Молчаливое послабление опаснее лишнего отказа: контур, переставший замечать
поломки из-за сбоя собственного разбора, хуже контура, который зря беспокоит
человека. Незнакомый стек ничего не ломает — он просто не получает ни
послабления, ни починки, пока в нём не настроят отчёт.

**B16.** Базовый прогон, упавший по таймауту или отказу окружения, — **не отказ
стадии**. Исход считается неразобранным (B15), разработка идёт дальше прежним
путём.

Отдельное дерево от базового коммита не несёт установленных зависимостей
(`node_modules`, виртуальное окружение). Там, где тесты без них не идут,
базовый прогон закономерно упадёт — и это штатный откат к сегодняшнему
поведению, а не дефект.

**B17.** Тест, переименованный агентом, считается **своим**: старого имени в
базовой линии нет, новое красное. Агент его тронул — он за него и отвечает.
Обратное правило дало бы способ спрятать поломку переименованием.

**B18.** Пустой `DEVELOP_TEST_COMMAND` — ни базовой линии, ни починки, как
сегодня.

### Что видит человек

**B19.** Чужая краснота при удавшемся прогоне называется прямо — в теле PR и в
комментарии: эти N тестов падали до правки, агент их не трогал. Умолчать
значило бы отдать на ревью PR с красным набором без объяснения.

**B20.** Отказ после неудавшейся починки перечисляет **только свои** падения и
говорит, что попытка починки была. Иначе человек не отличит «агент не смог» от
«контур не пробовал».

**B21.** Починка видна в ленте задачи отдельным сообщением: что сломалось, что
контур пробует сделать. Молчащий контур, который внутри себя делает второй
дорогой заход, неотличим от зависшего.

### Сигналы слою саморефлексии

**B22.** Сигнал `tests_passed` (`_write_signal`, `worker/activities.py:2975`)
отражает **свои** поломки, а не общую красноту: иначе слой считает неудачей
чистую работу в красном репозитории.

**B23.** Смена смысла `tests_passed` — **разрыв ряда**: в истории слоя
смешаются две семантики. Прогоны до выкладки писали «набор зелёный», после —
«агент не сломал своего». Признак версии смысла пишется рядом с сигналом,
чтобы свёртка могла разделить ряды, а не усреднять несравнимое.

**B24.** Чужая краснота пишется отдельным сигналом `tests_red_before`, факт
починки — сигналом о числе заходов. Слить их в `tests_passed` значит потерять
различие ровно там, где оно заводится.

### Прогон и его история

**B25.** Новые активности и новые ветки решения требуют `workflow.patched`.
Гвард `tests/test_workflow_replay.py` обязан остаться зелёным.

**B26.** Частичная выкладка (`dev_publish_partial`, PR #295) не меняется: отказ
после неудавшейся починки по-прежнему даёт черновой PR с работой агента —
включая то, что он написал в круге правок.

## Пограничные случаи

| Случай | Поведение |
|---|---|
| Итоговый прогон зелёный | Ничего лишнего не гоняется (B1) |
| База красная, после агента те же падения | Успех, обычный PR с оговоркой (B19) |
| База красная, агент починил её часть | Успех: своих поломок нет (B3) |
| Размен: починил один, сломал другой | Своё падение обнаружено, идёт починка (B3, B9) |
| Падение только в одном из двух прогонов | Мигающий тест, агенту не вменяется (B6) |
| Своя поломка, починка удалась | Успех, обычный PR (B14) |
| Своя поломка, починка не удалась | Отказ, черновик, человек (B10, B26) |
| Починка сломала ещё что-то | Отказ: заход был один (B10) |
| Отчёта нет ни до, ни после | Сегодняшнее поведение, починки нет (B15) |
| Базовый прогон упал без зависимостей | Не отказ; сегодняшнее поведение (B16) |
| Агент переименовал тест | Падение считается своим (B17) |
| `DEVELOP_TEST_COMMAND` пуст | Ни базы, ни починки (B18) |
| Прогон разработки идёт с прежним кодом | Реплей не ломается (B25) |

## Чем проверяется

- Разбор JUnit XML на реальных образцах `pytest` и `node --test`.
- Зелёный прогон не гоняет ни базовой линии, ни повторов.
- Своя поломка обнаружена; чужая пропущена; размен обнаружен.
- Падение, случившееся один раз из двух, агенту не вменяется.
- Починка запускается ровно на своих поломках и ровно один раз.
- Текст для повторного захода не содержит чужих падений.
- Удавшаяся починка даёт обычный PR; неудавшаяся — отказ и черновик.
- Неразобранный отчёт даёт прежнее поведение на любом конце.
- Отказ базового прогона не роняет разработку.
- Сигналы: `tests_passed` про своё, чужая краснота и число заходов отдельно,
  признак версии смысла на месте.
- Гвард реплея зелёный; правки решений под маркерами.

## Вне границ

- **Больше одного захода починки.** Настройка есть (B10), поднимать её без
  статистики нечем.
- **Починка чужой красноты.** Контур её называет, но не трогает: это чужая
  задача, и правка чужого кода под видом решения своей — худший исход, чем
  отказ.
- **Настройка отчёта в чужих репозиториях.** Механизм поддерживает,
  проставление по репозиториям — работа эксплуатации.
- **Починка красноты `main` демо-репозитория** (`tests/pricing.test.mjs`,
  незафиксированная дата) — задача самого демо-сервиса.
- **Прогон тестов на PR силами CI** и **CI по расписанию**, ловящий бомбы с
  часовым механизмом, — отдельные давние блокеры контура.
