# poh-developer-agents

**Стадия «Разработка» контура производства.** На входе — системные требования,
на выходе — проверенный код в пул-реквесте, годный к отгрузке на Production.

Стадия была построена и работает, но до сих пор не имела своего репозитория:
код жил в `poh-issue-agents` (сервис Issue и аналитики), обвязка — в целевом
репозитории, ревью — в `poh-pr-agents`, доводка — ещё и в `poh-pr-closer`.
Здесь она собрана в одном месте и описана как стадия, а не как набор активностей
чужого воркера.

> **Начать с [`AUDIT.md`](AUDIT.md)** — что именно построено на сегодня, где
> лежит и чего не хватает.

## Что делает стадия

```
system_requirements.md + ready-for-dev
        │
        ▼
  постановка агенту ─▶ агент пишет код ─▶ тесты ─▶ ревью ─▶ круг правок ─▶ мерж
   (требования +       (одноразовый      (гейт +   (PR-     (≤3 круга,
    правила репо)       контейнер,        диагноз   Agent)    иначе человек)
                        без токена)       + починка)
```

Пять решений, которые объясняют устройство:

**Агенту разработки не дают GitHub-токен.** Он **исполняет** код чужого
репозитория — ставит зависимости, гоняет тесты. Внутри воркера это означало бы
выполнение произвольного кода рядом с токеном и ключом модели. Прогон живёт
минуты в одноразовом контейнере, видит только каталог своей задачи и умирает
вместе с ней; коммит, пуш и PR делает воркер уже после, своими руками.

**Тесты гоняются до пуша, а не на PR.** PR, созданный `GITHUB_TOKEN`, не
порождает событий workflow — CI на нём не запустится вовсе. Без гейта внутри
прогона красный код уезжал бы в PR без единого признака того, что он красный.

**Своя краснота отличается от чужой.** Базовая линия на чистом дереве,
перепроверка на мигание, разница множеств имён из JUnit XML. Своя — чинится
одним повторным заходом агента. Чужая — публикуется как есть: она не наша.

**Признак «замечаний нет» — пустой дифф, а не разбор разметки ревью.** Парсить
формат чужого инструмента значит зависеть от того, что меняется без
предупреждения. Агенту отдаётся текст ревью и правило «исправь то, что требует
исправления; нечего по существу — не меняй ничего».

**Правила работы агента живут в целевом репозитории.** Их правит тот, кто правит
конвенции проекта. Строкой внутри workflow это значило бы спрятать контракт от
того, кому он адресован.

## Модули стадии

```
poh_developer/
  develop.py       контракт прогона: режимы, постановка, слаг задачи, служебные
                   файлы, команда раннера, разбор находок, резерв памяти хоста
  test_report.py   имена упавших тестов из JUnit XML — основа диагноза красноты
  pr_closing.py    круг правок: потолок кругов, метка очереди к человеку
  worktree.py      коммит и пуш рабочего дерева агента, общее для GitHub и GitLab
  runner.py        инварианты образа раннера, с которыми обязан совпасть образ
                   воркера в соседнем репозитории: мажор Node, uid
```

Все — только стандартная библиотека: ни сети, ни Temporal, ни GitHub. Это и
есть граница, по которой стадия вынимается из сервиса.

## Обвязка целевого репозитория

Что положить в репозиторий, который берётся под контур:

```
target-repo/
  .openhands/task-rules.md              правила работы агента (пришиваются к постановке)
  AGENTS.md                             постоянный контекст: структура, проверки, чего не делать
  CLAUDE.md                             полный свод правил репозитория
  .delivery/checks.json                 чем Delivery-Agent подтверждает поведение на проде
  .github/workflows/ci.yml              проверки PR и main
  .github/workflows/openhands-resolver.yml   разработка в режиме dispatch
  .github/workflows/pr-review.yml       ревью PR
```

Режим `local` (умолчание) обходится без двух последних: прогон идёт на стенде.

> ⚠️ `AGENTS.md` и `.openhands/task-rules.md` сегодня описывают механику находок
> (SubIssue), от которой контур отказался — см. [`docs/gaps.md`](docs/gaps.md),
> **G5**. Правка шаблонов — открытая задача.

