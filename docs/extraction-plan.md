# План соединения: как этот репозиторий встраивается обратно

> **Порядок работ принят отдельно.** Этот документ остаётся справкой о том,
> **что** и **почему** отобрано в пакет и как ловится расхождение копий, пока
> они существуют. Согласованный порядок и объём — в
> [`design/2026-09-05-developer-as-a-service-design.md`](design/2026-09-05-developer-as-a-service-design.md)
> и плане [`design/2026-09-05-developer-as-a-service.md`](design/2026-09-05-developer-as-a-service.md):
> решено доводить стадию до **своего сервиса** (четыре захода), образ тянуть
> плавающим `main`, код — пином по тегу.

Настоящий репозиторий собран **копированием**, а не переносом: `poh-issue-agents`
продолжает работать на своих копиях модулей, и стенд от появления этого
репозитория не изменился ничем. Это осознанный первый шаг — вынимать код из
работающего контура одним движением значит проверять его сразу на живом прогоне.

Тот же путь прошёл `poh-sysreq-agent`: сначала отдельный репозиторий с ролью и
шаблонами, потом задача на встраивание обратно
([`poh-issue-agents#70`](https://github.com/po-helper-org/poh-issue-agents/issues/70)).

здесь и не доехавшая туда, не влияет ни на что; правка, сделанная там и не
доехавшая сюда, делает этот репозиторий враньём. Расхождение обнаруживается
`make drift` (см. ниже) и должно закрываться в тот же день.

## Почему именно эти четыре модуля

Отбор не по теме, а по **зависимостям**: у всех четырёх импорты — только
стандартная библиотека.

```
develop.py      os, pathlib, shlex
test_report.py  logging, pathlib, xml.etree
pr_closing.py   os
worktree.py     logging, os, subprocess
```

Ни сети, ни Temporal, ни GitHub, ни импортов из соседних модулей контура. Это
ровно та граница, по которой стадию можно вынуть, не разбирая сервис: остальное
(`activities.py`, `workflows.py`, `github_client.py`) — ввод-вывод и оркестрация,
они принадлежат тому, кто держит воркер.

**Что по теме подходит, а по границе — нет.** `shared/review_events.py` (разбор
события ревью GitHub в факт для цикла) — часть круга правок и, казалось бы,
принадлежит стадии. Но он импортирует `shared.lifecycle` и
`shared.agent_events`: его выход — `AgentEvent`, тип **цикла задачи**, а не
стадии. Забрать его сюда значило бы утащить следом словарь фаз и протокол
событий, то есть половину `poh-issue-agents`. Он остаётся там, а стадия знает о
нём только то, что замечания человека доезжают до круга правок тем же путём,
что и доклад PR-Agent.

Критерий отбора здесь важнее списка: **берём то, у чего нет зависимостей от
контура, а не то, что по смыслу «про разработку».** Второй критерий не имеет
границы и кончается переносом сервиса целиком.

## Шаг 1. Пакет ставится в образ воркера

Образец уже есть и работает — `poh-delivery-agent` подключён к харнессу ровно
так: пакет ставится в образ воркера, обратной зависимости нет.

```dockerfile
# poh-issue-agents/worker/Dockerfile
RUN pip install --no-cache-dir \
    "poh-developer @ git+https://github.com/po-helper-org/poh-developer-agents@<тег>"
```

Версия фиксируется **тегом или коммитом, а не плавающим HEAD**: правка контракта
стадии равносильна правке кода и должна проходить ревью, прежде чем попасть в
прод-пайплайн.

## Шаг 2. Импорты в `poh-issue-agents` переставляются

```python
# было
from shared import develop, pr_closing, test_report
from worker.worktree import publish            # внутри воркера: import worktree

# станет
from poh_developer import develop, pr_closing, test_report
from poh_developer.worktree import publish
```

Оговорка раскладки, о которой легко забыть: `worker/` и `webhook/` в
`poh-issue-agents` **не пакеты** — Dockerfile расплющивает их в `/app`, и
`from worker.X import ...` в контейнере падает. Установленный пакет этой
проблемы не имеет: `poh_developer` резолвится одинаково и в тестах, и в образе.
Это ещё один довод за пакет, а не за submodule.

## Шаг 3. Копии удаляются

`shared/develop.py`, `shared/test_report.py`, `shared/pr_closing.py`,
`worker/worktree.py` удаляются из `poh-issue-agents`. С этого момента источник
правды — здесь.

Тесты, которые останутся в `poh-issue-agents`, — те, что проверяют **связку**
(активности, воркфлоу, порядок шагов). Тесты чистых модулей живут здесь.

## Шаг 4. Образ раннера собирается отсюда

```yaml
# poh-infra/harness/docker-compose.yml
openhands-runner:
  build:
    context: "${DEVELOPER_AGENT_CONTEXT:-https://github.com/po-helper-org/poh-developer-agents.git#main}"
    dockerfile: agent/Dockerfile
  image: "${DEVELOP_RUNNER_IMAGE:-poh-openhands-runner:local}"
```

Сегодня контекст указывает на `poh-issue-agents`, а Dockerfile лежит в
`openhands/`. После переноса — сюда, в `agent/`.

**Зависимость, которую нельзя потерять:** тест
`test_worker_and_runner_agree_on_the_node_version` сверяет мажор Node между
`worker/Dockerfile` (там) и `openhands/Dockerfile` (здесь). После разъезда по
репозиториям сверять станет нечего, и инцидент прогона #13 сможет повториться.
Инвариант нужно перевесить: мажор Node объявляется здесь константой, а
`poh-issue-agents` сверяется с ней.

## Шаг 5. Шаблоны целевого репозитория раскатываются отсюда

`target-repo/` — образец обвязки. Сегодня она копируется из `poh-demo-checkout`
по памяти, и уже разошлась с поведением контура (см. [`gaps.md`](gaps.md), G5).
После переноса правка делается здесь один раз, а целевые репозитории берут её
явным шагом.

## Сверка расхождения

Пока копий две, расхождение обязано быть видимым:

```bash
make drift        # diff между poh_developer/*.py и shared/*.py в poh-issue-agents
```

Скрипт клонирует `poh-issue-agents` на `main`, сверяет четыре файла и Dockerfile
и падает, если они разошлись. Гоняется в CI по расписанию — расхождение находит
не человек на разборе, а прогон.

## Порядок и риск

| Шаг | Риск | Откат |
|---|---|---|
| 1. Пакет в образ | нет — код не используется | убрать строку |
| 2. Переставить импорты | средний: контейнер расплющивает пути | вернуть импорты |
| 3. Удалить копии | **точка невозврата** | revert коммита |
| 4. Образ раннера отсюда | средний: ломает сборку харнесса | вернуть контекст |
| 5. Шаблоны | низкий | — |

Шаги 1–2 делаются одним PR и проверяются полным прогоном стенда с `DRY_RUN=1`.
Шаг 3 — отдельным PR, **после** зелёного живого прогона разработки, а не вместе
с ним: иначе разбор «почему сломалось» упрётся в два изменения сразу.
